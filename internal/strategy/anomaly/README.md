# AnomalyDetector Strategy

## Назначение

Стратегия для обнаружения **аномалий** в движении цены, объема и трейдов на основе **статистического z-score**.

## Как это работает

### 1. Сбор данных

Для каждой пары (например BTCUSDT) для каждого настроенного периода (15m, 1h, 4h, 1d) собираются значения метрик:

| Метрика | Источник | Что означает |
|---------|----------|-------------|
| `price` | `ChangePrices[pair][period].ChangePercent` | Изменение цены за последнюю минуту |
| `volume` | `ChangeDelta[pair][period].Volume` | Изменение объема во втором полупериоде относительно первого (%) |
| `volumeBuy` | `ChangeDelta[pair][period].VolumeBuy` | Агрессивный buy объем (%) |
| `volumeAsk` | `ChangeDelta[pair][period].VolumeAsk` | Агрессивный sell объем (%) |
| `trades` | `ChangeDelta[pair][period].Trades` | Количество трейдов (%) |
| `tradesBuy` | `ChangeDelta[pair][period].TradesBuy` | Агрессивные buy трейды (%) |
| `tradesAsk` | `ChangeDelta[pair][period].TradesAsk` | Агрессивные sell трейды (%) |

### 2. Накопление истории

Для каждой пары + периода + метрики хранится **кольцевой буфер** (по умолч. 30 значений).

Значение пишется в буфер **не чаще одного раза за период**, а не каждую минуту. Источники (`ChangePrices`/`ChangeDelta`) пересчитываются каждую минуту скользящим окном, поэтому соседние минутные значения почти идентичны (окно сдвигается на 1 минуту из `period`): если писать их все, разброс будет занижен и z-score сломается. Проверка (расчёт z) при этом происходит **каждую минуту** — троттлится только запись в историю.

**Сидирование из БД.** При старте буферы заполняются из таблиц `candles_{period}` (их пишет feederapp). Агрегированная свеча периода — это ровно одна выборка истории: `price` в рантайме = `close(t)/close(t−P) − 1`, а дельта объёма = объём за последние `P` против предыдущих `P`, то есть и то и другое равно отношению соседних свечей таблицы. Поэтому история восстанавливается один-в-один. Без этого детектор на `4h` выходил бы на боевой режим несколько суток, а каждый рестарт бота обнулял бы накопленное.

### 3. Z-Score

Для каждого нового значения вычисляется **робастный z-score** — по медиане и MAD (median absolute deviation), а не по среднему и стандартному отклонению:

```
z = (текущее_значение - медиана_истории) / (1.4826 * MAD)
```

Множитель `1.4826` приводит MAD к шкале сигмы нормального распределения, поэтому пороги читаются привычно. Медиана и MAD нужны потому, что у крипты тяжёлые хвосты: одно прошлое экстремальное значение, осевшее в буфере, раздувает `stddev` настолько, что следующая настоящая аномалия уже не проходит порог. Если MAD вырождается в 0 (больше половины значений одинаковы — например, объём стабильно нулевой), используется среднее абсолютное отклонение.

**Метрики-дельты** (`volume*`, `trades*`) перед расчётом логарифмируются: `log(1 + value/100)`. Дельта — это отношение «новое окно / старое окно», снизу оно ограничено −100%, а сверху не ограничено ничем, то есть распределение сильно скошено вправо (падение объёма вдвое = −50%, рост вдвое = +100%, хотя события одинаковы по силе). Логарифм делает метрику симметричной. Цена уже симметрична и логарифмированию не подвергается. В уведомление всегда уходит **сырое** значение — его читает человек.

**`minSamples`** (по умолч. 20): пока в буфере меньше этого числа значений, z-score не считается вообще. На 2–3 значениях разброс оценивается по шуму, и любое рядовое значение получает z=10.

**`minScale`** — нижняя граница разброса. У стейблкоинов цена практически стоит, у неликвида объём месяцами не шевелится: MAD вырождается почти в ноль, и движение на 0.01% честно даёт z=6, а падение объёма на 99% — z=−61. Пол разброса возвращает такие z в осмысленный диапазон.

**`minDailyVolume`** — фильтр ликвидности по суточному обороту (`MarketsStat.Volume` = `QuoteVolume` за 24ч, сразу в USDT). Пары ниже порога не проверяются вообще. Это главный фильтр мусора по объёму: у неликвида оборот предыдущего окна близок к нулю, поэтому дельта выдаёт `+87000%` там, где два человека что-то купили. Проблема тут не в величине изменения, а в **величине базы**, и порогом `minChange` она не лечится.

**`minChange`** — порог экономической значимости в сырых процентах. Z-score меряет **статистическую неожиданность, а не силу события**: даже с полом разброса движение стейблкоина на 0.03% остаётся статистически редким. Если изменение меньше `minChange`, срабатывание гасится независимо от z, и такая метрика не попадает в composite.

- **z ≈ 0** — значение близко к норме
- **\|z\| >= 3.0** — заметное отклонение от нормы
- **\|z\| >= 5.0** — экстремальная аномалия
- **\|z\| >= 8.0** — критическая аномалия

Важно: пороги 3/5/8 калиброваны под нормальное распределение, а рынок ненормален — z≥3 случается чаще, чем «в 0.3% случаев». Плюс каждую минуту делается `пары × периоды × метрики` проверок, так что при 40 парах порог `level1: 3.0` на коротких периодах даст шум. В `config.example.yaml` для `15m` он поэтому поднят до 4.0.

### 4. Уровни аномалий

Каждый период имеет **3 порога** (level1, level2, level3):

| Уровень | Иконка | Условие | Cooldown |
|---------|--------|---------|----------|
| 0 | — | z < level1.threshold | Нет аномалии |
| 1 | ⚠️ | z >= level1.threshold | = длительности периода |
| 2 | 🔴 | z >= level2.threshold | = длительности периода |
| 3 | 🚨 | z >= level3.threshold | = длительности периода |

### 5. Cooldown (защита от спама)

После отправки уведомления устанавливается **cooldown = длительность периода**, взятая из основного конфига приложения (`ChangePeriods`), а не из собственной таблицы стратегии:
- Для 15m → ждем 15 минут до следующего уведомления
- Для 1h → ждем 1 час
- Для 4h → ждем 4 часа
- Для 1d → ждем столько, сколько этот период реально длится по конфигу (сейчас в `root.go` `1d` задан как 12 часов)

**Исключение**: если аномалия **усилилась** до более высокого уровня (например, была level1, стало level2) — отправляется новое уведомление, и cooldown сбрасывается заново.

Важно: `lastLevel` сбрасывается в 0 **только после истечения cooldown**. Если сбрасывать его на каждой спокойной минуте, метрика, болтающаяся вокруг порога, будет слать уведомление каждую минуту: правило эскалации увидит `1 > 0` и пропустит алерт мимо ещё активного cooldown.

### 6. Пример

Все аномалии одного тика уходят **одним дайджестом**. Отдельным сообщением на пару это нечитаемо: на рыночном движении аномальными становятся сотни пар одновременно.

Группировка идёт **по паре**, а не по периоду: одно и то же движение обычно видно сразу на нескольких периодах, и разносить его по разным секциям — значит заставлять читателя самому сопоставлять строки. Пара — это то, о чём принимается решение, поэтому она и есть единица дайджеста. Внутри пары периоды идут от коротких к длинным, сами пары — от сильнейшей аномалии к слабейшей.

```
📊 Аномалии (19:18): 3 пары

🚨 ADAUSDT
   1h z=8.4 | price +2.96%, volume +482.94%
🚨 SXTUSDT
   15m z=7.5 | price +6.08%
   1h z=8.2 | price +5.94%
🔴 TUSDT
   15m z=-6.2 | price -4.64%
```

Сколько пар показывать — `digestMaxItems`, остальные схлопываются в «… и ещё N пар».

### 7. Рыночная метрика

Помимо уведомлений по отдельным парам, стратегия отслеживает **долю аномальных пар** от общего числа. Если эта доля превышает `anomalyPercentThreshold`, отправляется рыночное уведомление:

```
🌍 Рыночная аномалия (1h)
  45.0% пар аномальны (18 из 40)
  Топ аномалий:
    ⚠️ BTCUSDT: z=4.2 [Уровень 2]
    🔴 SOLUSDT: z=3.9 [Уровень 2]
    ⚠️ GALAUSDT: z=3.7 [Уровень 1]
```

Рыночная метрика также использует cooldown = длительности периода, причём **свой на каждый период**: сработавшая аномалия по `1d` не должна глушить рыночные уведомления по `15m` и `1h`.

Доля считается по **всем** аномальным парам, а не только по тем, чьи персональные уведомления прошли фильтр cooldown — иначе процент занижался бы.

## Конфигурация

Актуальный пример со всеми полями и пояснениями — в [config.example.yaml](config.example.yaml). Ключевые параметры:

| Параметр | Смысл |
|---|---|
| `historyWindowSize` | Размер буфера истории (медиана/MAD). Можно переопределить для каждого периода отдельно. |
| `minSamples` | Пока в буфере меньше этого числа значений, z-score не считается. Защита от мусорных алертов, когда в БД мало свечей. |
| `minChange` | Минимальное изменение метрики (сырые %), ниже которого срабатывание гасится независимо от z. Отсекает стейблкоины и микродвижения. |
| `minScale` | Нижняя граница разброса (MAD). Не даёт z взорваться до 30–80 там, где метрика почти всегда стоит на месте. |
| `minDailyVolume` | Минимальный суточный оборот пары в USDT. Неликвид не проверяется вообще. |
| `digestMaxItems` | Сколько строк показывать в дайджесте на один период. |
| `minNotifyLevel` | Минимальный уровень для попадания в дайджест (2 — только 🔴 и 🚨). В рыночной метрике отсечённые уровни всё равно учитываются. |
| `metrics` | Каждая включённая метрика — ещё один шанс на ложное срабатывание (composite = max\|z\|). |
| `thresholds` | Пороги z для уровней 1/2/3. На коротких периодах (`15m`) стоит держать `level1` выше. |
| `marketMetric.anomalyPercentThreshold` | Доля аномальных пар (%), при которой шлётся рыночное уведомление. |

## Интеграция в проект

Стратегия автоматически создается в `ControllerStrategy.build()` (файл `internal/strategy/strategy.go`). Она подписывается на канал `AssetsPrices.UpdateChanel` и запускается в `StartAll()` вместе с остальными стратегиями.

## Зависимости

- `AssetsPrices` — поставщик ценовых и дельта-данных
- `Notification` — отправка сообщений (Telegram и др.)
